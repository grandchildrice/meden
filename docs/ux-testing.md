# Testing the developer experience

The unit of acceptance is a developer completing a task from the public TUI.
A model saying “done”, a successful tool call, or a screenshot alone does not
establish completion. Keep this checklist current when changing the workflow.

## Run the required journeys

From the repository root, after building the binary:

```bash
cargo build -p meden-cli
MEDEN_BIN="$PWD/target/debug/meden" uv run --project python --group dev \
  python -m meden_checks.ux --out /tmp/meden-ux-review
```

Use a new output directory for each run. Open `/tmp/meden-ux-review/index.html`
to select a journey and move through its decoded terminal screens. `summary.json`
and `junit.xml` contain the verdicts; the summary identifies the binary by path
and SHA-256; individual directories retain timestamped
`screens.jsonl` and `last-screen.txt`. Screen records are sampled after PTY reads,
not a recording of every paint. Per-test traces are capped at 10 MB and indicate
truncation in `trace.json`; the final screen is retained separately.

The command needs the Python dev dependencies, Linux, Bubblewrap, public Z3, an actual
installed Lean/Lake distribution (`MEDEN_ATLAS_LEAN`) and the host public toolchain used by the existing integration tests. A missing prerequisite,
skipped journey, failed assertion or empty selection fails the required gate.
Fixtures use temporary projects, synthetic replies and an inert project-checker
manifest. The required Lake journey additionally uses the actual installed
Lean/Lake package loader and compiler. These are installed prerequisites, not
paid-model or cold-install validation. CI downloads the same pinned public Lean
distribution used by the native GUI journeys.

Run the Python lint check from `python/`, matching CI:
`uv run --group dev ruff check . ../tools ../crates/meden-runtime/src/pages/network_fixture.py`.
The working directory affects Ruff's fallback configuration and import discovery;
checking the same paths from the repository root is not the same check.

CI runs these same marked cases once within the existing Python adapter job.
The public runner starts its test process in a fresh session so each journey
uses its configured PTY size instead of inheriting the launching terminal.
`test_ux_gate.py` also exercises that runner inside a real 80×24 controlling
terminal; its inner journeys retain their own sizes and decoded evidence.
It uploads `meden-ux-evidence`, including the HTML viewer, on success or failure.
Other platform-dependent tests may still skip; required `ux` cases must pass.

## Experience contract

Workspace/model-session changes must preserve the public processor-review,
connection replacement, failed-provider recovery and restart journeys. Reopening
retains original conversations and prepared graphs, but requires fresh model
approval. The host workspace identity stays distinct from reviewed-contract and
publication identities. Compile examples reject cross-context and raw-byte model
calls; finite arbitrary-byte processor traces compare the exact original kernel
parameters/outcomes. An actual loopback HTTP test checks equal copied identities,
non-UTF-8/NUL differences, no request before approval and terminal revocation.
These are adapter/type checks, not live-model quality or new kernel refinement.

Snapshot-context changes must preserve original digest framing and complete
source/graph data. Source, graph and prepared-input revisions cannot be exchanged
as Rust values; canonical wire spelling still does not confer origin or authority.
The native meaning journey sends 21 malformed source/graph identity bodies to
the actual command endpoint, requires refusal before queuing or inference, then
completes ordinary analysis and historical restart. A null graph remains valid
lexical syntax; actual host comparisons still reject mismatched contexts. The
same driver against the original executable must fail the refusal condition at
HTTP 202 rather than a startup/prerequisite error. Backend definition changes
require fresh bound artifacts once; subsequent restart must reuse them without
compilation/search/rendering. Old artifacts must not be relabeled.

Compiler/search/render cache contexts retain their original bare digests and
complete parent/body checks. The actual body's type selects its storage role;
decoded identity spelling does not grant ownership. Public source preparation,
search-settings, renderer-update, compiler-failure and restart journeys must
still pass. When a search method's schema/codec changes, execute its new search
once while retaining the exact original compiler and rendering artifacts;
subsequent tab returns and restart reuse the new result without semantic workers
or model approval. Type examples and generated byte-framing cases cover the
cache boundary separately from public installed-tool behavior.

## Completion criteria for changes

When changing data/application boundaries, also run `npm run architecture:check`.
Its negative cases check the structural guard, not live backend quality.
The shared `meden-app` layer cannot depend on presentation or concrete model
transports. Public Atlas/Lake, meaning with a separate judge, repair and native
verification journeys exercise the application extraction; compiler registration
must reject unknown/duplicate keys, and the model port must preserve terminal
revocation without sending. The
native startup/retained-tab journeys and recorded-workspace import/edit/restart
journeys exercise the actual browser adapter and evidence invalidation. Pure
workspace transitions receive explicit identity/time so replay is reproducible.
Native source projection changes also exercise the lexical source, real offline
Atlas, prepared Lake and retained-tab browser journeys. Projection checks cover
namespaces, comments, privacy, original lines, oversized UTF-8 refusal, stale
source bindings, duplicate IDs, missing targets and valid cycles. Generated
schema checks cover the owned vocabulary and reject unsupported constraints;
they are not a general JSON Schema equivalence proof. The source/graph projection
does not carry current accepted-contract evidence.

The verification-progress journey holds only the original checker's dispatch
through an explicit trusted host `MEDEN_BWRAP` launcher outside the workspace.
The issued check is cancelled before Z3 starts; after release the unchanged
Bubblewrap arguments run the actual installed solver and independent exhaustive
checker. A delayed progress response cannot replace cancellation. A separately
held model response proves that evidence completion and source-edit invalidation
publish before the next reply. Stop is acknowledged before that response is
released; this does not measure model-transport abort latency. Scripted inference
and this launcher timing fixture are not live-model or cold-install validation.

The proposal-observation journey uses the finite backend's actual bounded-data
validation, which requires no external compiler or solver. Its completed draft
remains unaccepted and cannot display implementation evidence. Response
failure/delay affects transfer only; retry must neither dispatch a command nor
make another model request. A later proposal retires the old body, and restart
keeps the proposed meaning without restoring a job or model approval. Separate
proposal check/record/total timers observe actual application boundaries; this
journey makes no compilation-speed or live-model claim.

The prepared-Lake browser journey requires exactly one requested-file inspection
after each explicit refresh, even when fast directory work finishes within one
React batch. Its cached build log must contain one batched Lake query and the
completed file/byte validation. The real compiler remains responsible for builds,
dependency edits, rejection and retry; protocol fixtures do not substitute for
those installed-tool journeys.

The native metadata-update journey builds two actual executables differing only
in the embedded input-validation helper. The companion repair-update journey
changes the embedded Lean repair method and its composition facade; those peer
changes must reuse the original compiler/search/render objects too. Real Lake
configuration, compile-time project code and imported initialization refuse helper and generic-worker
visibility. After restart, complete input validation must still run while the
original source view and all compiler/search/render artifact files remain
identical, without those workers
or model requests. A failed real query must not dispatch metadata validation.
The test builder uses its own target and forces fresh workspace-package builds;
equal executable hashes or missing embedded helper bytes fail the journey.

The fading-area journey uses 128 actual indexed Lean files, native inventory
workers, observed Canvas drawing and a real keyboard focus/Enter sequence.
Below the pointer threshold, area paint remains while unused SVG targets are
absent. The focused target stays mounted, accessible and visibly highlighted
until focus leaves, including during fading. Painted areas and hit targets
preserve their original relative geometry/order; their counts may differ.
The unchanged deployed renderer must fail this target budget. A separate
visibility-consumer budget rejects repeated traversal for identical cloned
viewport inputs, while complete scan/corpus checks retain resize and scene
invalidation. These are presentation checks, not new verification authority.

## Exploratory review before declaring a new flow usable

Use a fresh temporary project with synthetic data. Give an evaluator (human or
AI) only a goal, the README entry command and the visible TUI, for example:
“Start a project, implement a small calculation, close the app and continue it.”
For a new flow, also try a provider error, a long silent response and a small
terminal. Do not supply internal key sequences, edit private configuration or
read source to rescue the evaluator. Record each place where progress requires
guessing, an unexplained stop, an extra command, lost work or ambiguous proof
status. Save the screens and turn reproducible problems into deterministic tests.

An AI implementation agent should do this screen review as part of its completion
criteria. This is a review procedure, not a separate autonomous evaluator service;
the current automation cannot judge taste or discover every unknown workflow.
The developer should need to review new choices, rather than repeat old regressions.

## Live-model smoke

For changes to prompting, tool use or multi-turn behavior, and before a release,
run the separate driver with an explicitly selected capable Ollama Cloud provider
already configured on the host:

```bash
uv run --project python --group dev python -m meden_checks.tui_smoke \
  --binary target/release/meden --provider YOUR_PROVIDER --model YOUR_MODEL \
  --out /tmp/meden-live-review.json
```

This approves the chosen processor through its real review screen for a synthetic
project, fixes a program, restarts the TUI with fresh review, adds a feature using
the retained conversation and checks the result independently in an offline copy.
It saves source, original-test preservation, exit status and milestone screens.
CI tests the driver against a scripted provider, including a lying completion
with broken code. That protects the driver from stale controls; it is not live
inference evidence. A real cloud run is not local-model or confidentiality evidence.
No live requests or model performance claims are part of the fast gate.

The separate reviewed-repair smoke uses the public TUI, preserves the original
requirement and runs independent Rust boundary tests in an offline copy:

```bash
uv run --project python --group dev python -m meden_checks.meaning_smoke \

  --verifier-bundle /absolute/path/to/installed/bundle.json \
```
