# Keep job observations with their original owner

Preparation logs and verification progress previously retained job identities
as ordinary strings. Their publishers already rejected replaced, completed and
backwards-time observations. They now carry `JobId<Owner>` through the actual
producer handles, current statuses and frozen bodies, so a preparation identity
cannot accidentally become a verification observation or a content query.

The type has no transport decoder or public constructor. Each original producer
supplies its computed SHA-256 result. Project checks and portable-work checks
share their existing verification publication owner and continue to distinguish
their original subject, origin and application stages. This adds no controller,
compatibility path, dependency, new serialization pass or polling work.

The original three domain separators, exact host/input bindings and sequence
encoding remain unchanged. Independent fixed fixtures cover UTF-8 preparation
paths, a proposed finite contract and a historical model-origin check. Generated
JSON schemas and browser codecs remain byte-identical. The Rust distinction is
not present in JSON and does not establish ownership of a client-supplied string.

Validation uses the complete application unit suite, matching/rejected compile
examples and the public TUI gate with decoded failure/restart screens. Actual
browser journeys exercise streaming compiler logs, timeout/cancellation/retry,
delayed progress replacement, proposal-only meaning, retained source tabs and
portable-work restart. They use installed Lean/Lake and Z3 with scripted model
responses; this is neither live-model quality nor cold-install validation.

The checked native executable is kept at an immutable path throughout these
journeys. The thirteen compiler-captured implementation sources and complete
deployed browser assets are compared with the preceding deployment, so this
type change must not invalidate original compiler observations or graphs.
The validation record is
[job-observation-identities-20261125.json](../../results/job-observation-identities-20261125.json).
The deployment helper initially exhausted its short readiness polling for
EthLib. Both new processes were subsequently verified through authenticated
status, their exact executable and every served asset, without another restart.
The record retains that failed helper attempt separately from the passing
public journeys; it does not infer which initial readiness predicate was absent.

The same final actual-project probes still take 20.234 s for Riemann and 2.225 s
for EthLib from file click to prepared-source DOM. Riemann's correlated Lake
preparation lasts 15.854 s; its worker log attributes 10.961 s to build/setup/input
resolution and 4.278 s to complete-byte validation of 43,477 files / 5,992,114,707
bytes. These are nested, unpaired fidelity observations, not a timing comparison
or speedup claim. They keep the remaining native wait separate from map painting.

These identities remain read-only observations. Execution tickets, acceptance,
evidence admission and original host comparisons still belong to their existing
controllers. This adds no Lean refinement claim or measured speedup. The event
measurements remain in [the map-paint report](map-area-paint.md); backend
snapshots, other session representations and the remaining identity/retirement
audit are still open.
